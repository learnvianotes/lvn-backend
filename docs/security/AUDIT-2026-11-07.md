## Findings

### F1 — Critical. Provider sign-in adopts an unconfirmed email and keeps the squatter’s password

**Location:** `contexts/users/src/application/oauth.service.ts:103` (link), fixed at `:110`.

**Scenario:** Sign-up creates an account and a session before the address is confirmed (`auth.service.ts` signs the new account in immediately). Anyone can register `victim@gmail.com` and set a password. When the person who owns that inbox later signs in with Google, GitHub, or LinkedIn, and the provider says the email is verified, `signInWith` linked the provider onto the existing row, set `emailVerifiedAt`, and left `passwordHash` and every existing session in place. The provider user landed in the squatter’s account. The squatter kept the password and the original access token, so notes, classes, and later activity stayed reachable to both.

A confirmed address is a different case: both sides have proved the inbox, and linking must keep the password. That path is unchanged.

**Fix:** When the existing row’s email is not confirmed, the link clears `passwordHash` and `SessionService.revokeAll` runs after the transaction commits. The provider session is started after that revocation. Covered by `apps/api/test/e2e/oauth-registration.e2e.test.ts` (Google onto an unconfirmed address: password sign-in fails, the old access token no longer resolves `viewer`, the new Google session does).

The squatter’s display name and any notes they wrote on that row remain. Wiping them would also wipe a legitimate user who signed up and then used Google before clicking the verification link.

### F2 — High. `X-LVN-Client: mobile` put the refresh token in the JSON body

**Location:** `contexts/users/src/graphql/session-delivery.ts:33` (`deviceOf`), delivery at `:49`.

**Scenario:** Web sessions store the 30-day refresh token in the HttpOnly `lvn_rt` cookie (`path=/graphql`, `SameSite=Lax`, `Secure` when `JWT_ISSUER` is `https://`). Delivery used to treat any request with `X-LVN-Client: mobile` as native and return `refreshToken` in the GraphQL payload, and skip the cookie. That header is not a forbidden header. Script running in the browser (an XSS on an allowed origin, or a compromised page) can set it on `signUp`, `signIn`, `refreshSession`, or a provider sign-in and read the long-lived token from the JSON. The HttpOnly flag then does not protect the session. A native app needs the token in the body; a browser does not.

**Fix:** Browsers send `Sec-Fetch-Site`, `Sec-Fetch-Mode`, or `Sec-Fetch-Dest`, and page script cannot strip those. If any of them is present, the refresh token stays in the cookie and the payload field is null, even when the mobile header is set. A client that does not send `Sec-Fetch-*` (the native app, and the existing supertest mobile helper) still receives the body token. Unit tests: `contexts/users/test/unit/session-delivery.test.ts`. End-to-end: `apps/api/test/e2e/auth.e2e.test.ts`.

### F3 — High. Sign-up and password reset had no per-network ceiling

**Location:** `contexts/users/src/application/auth.service.ts:76` (`signUp`), `:225` (`requestPasswordReset`). Limits: `contexts/users/src/domain/rules.ts:33` and `:39`.

**Scenario:** Sign-in is capped at 5 attempts per address per 15 minutes and 50 failures per network (`clientNetwork`: one IPv4, or an IPv6 `/64`). Password reset was 3 per address per hour. Verify-resend, link-email, and the institutional OTP are capped per user. Sign-up was not capped at all, and each new address sends a verification email (and an institutional code when one is supplied). Reset mail could be sprayed across many addresses from one network because the cap was per address. Anonymous callers are also outside the per-person GraphQL limit (F5), and one operation can carry many aliased mutations up to the complexity cap, each of which runs `signUp`.

**Fix:** After the email parses and before hashing or sending mail:

- `signup:<network>` — 300 per hour
- `reset-net:<network>` — 40 per hour, in addition to the existing 3 per address

300 is deliberately above a classroom behind one NAT and above what the test suite creates from loopback against the shared Redis. It stops an unbounded script. Unit tests: `contexts/users/test/unit/auth-network-limits.test.ts`. Tightening 300 is an owner decision (below).

### F4 — High. College ID uploads skip malware scanning

**Location:** `contexts/notes/src/application/files.service.ts:282`. Reviewer download: `contexts/users/src/application/verification.service.ts:315` (`collegeIdUrl`) and `:197` (`documentUrl`).

**Scenario:** Other uploads publish `FileReady` and are scanned (local `clamd`, or the remote scanner when `SCAN_MODE=remote`) before they are served. `finalizeCollegeIdUpload` checks size and magic bytes, then marks the object `READY` and does not publish `FileReady`. The comment cites ADR-0099 and ADR-0102: the media pipeline would write derivative copies of an identity document. `readUrls` serves `scanResult` null (`files.service.ts:376`). A reviewer who may see the request gets a presigned GET. A JPEG, PNG, WebP, or PDF that matches its declared type is enough. A malicious PDF or image that a reviewer’s viewer will parse was never scanned.

Presign scope, content-type, size (5 MB), and the object key (`{env}/{ownerId}/{fileId}/original`) are sound. The gap is the missing scan.

**Fix (not applied):** Scan the object and record `CLEAN` or quarantine it before any reviewer URL is issued, and do not run the image/video derivative step for `purpose = COLLEGE_ID`. Routing these files through `FileReady` would violate the ADR. Fail-open versus fail-closed when ClamAV is down is the same policy question as F7. Left for the owner.

### F5 — Medium. Anonymous GraphQL is not rate limited in the process

**Location:** `apps/api/src/app.module.ts:52`. The plugin is `libs/graphql/src/limits.ts:64`.

**Scenario:** `didResolveOperation` asks the app only when `viewer` is set. Anonymous traffic (public queries, `signUp`, `signIn`, `refreshSession`, provider sign-in, `requestPasswordReset`) is limited by depth, complexity, and the per-mutation windows, not by a process-wide counter. The code says address floods are for the edge (AWS WAF) because one address may be a campus. That is a real product constraint. Without the edge control, one host can still run expensive public queries up to complexity 1000, sixty times a second, from as many connections as it can open. F3 bounds the mail-sending mutations. It does not bound read load.

**Fix:** Keep the edge limit. If the API is ever exposed without it, add a separate, higher per-network budget for anonymous operations, with a ceiling the campus NAT can live under. Not changed here.

### F6 — Medium. Google, GitHub, and LinkedIn sign-in have no limiter

**Location:** `contexts/users/src/application/oauth.service.ts:52` and `:62`.

**Scenario:** Password sign-in is limited. `signInWithGoogle` verifies a Firebase ID token and `oauthExchange` calls the provider token endpoint with no Redis window. An anonymous client can spend CPU and provider quota until F5’s edge control answers. PKCE and the redirect allowlist are in place (`oauth.service.ts:65`).

**Fix:** A per-network window on `signInWithGoogle` and `oauthExchange`, similar to F3. Not changed here so a campus sign-in day is not locked out by a guessed number.

### F7 — Medium. A local scan that never answers still leaves the file served

**Location:** `contexts/notes/src/application/media-processing.service.ts:143`. Serving rule: `contexts/notes/src/application/files.service.ts:376` (`scanResult` `ERROR` is served; `PENDING` and `FAILED` are not).

**Scenario:** In `SCAN_MODE=local`, the last failed attempt (scanner down, or the file rejected as too large) sets `scanResult = ERROR` and the file stays downloadable. Remote mode leaves the file unserved until a clean verdict. `SCAN_MODE=off` never scans. Both are explicit. An attacker who can keep ClamAV down, on a deployment that uses local mode, gets uploads served unscanned.

**Fix:** In production local mode, treat `ERROR` like `FAILED` (do not sign a GET) or fail the upload closed. That changes availability when ClamAV is down, so it is left as a policy choice.

### F8 — Medium. Structured logs keep email addresses

**Location:** `libs/observability/src/logger.ts:10`. Locked in by `libs/observability/test/logger.test.ts` (the test expects `input.email` to survive redaction).

**Scenario:** Pino redacts authorization, cookies, `Set-Cookie`, passwords, tokens, OTP `code`, `dateOfBirth`, `age`, and `apiKey` one level deep. Request bodies and GraphQL variables are not logged. Email is not on the redact list, and a log line that includes an input object will store the address in Loki or CloudWatch. Sentry is stricter: `libs/observability/src/error-reporting.ts` turns off user info, cookies, bodies, query strings, and GraphQL documents, scrubs emails and bearer tokens in messages, and keeps only `user.id`.

**Fix:** Add `email` and `*.email` to `REDACTED_PATHS` and update the logger test, if support does not need the address in logs. Left, because the test records a deliberate choice.

### F9 — Medium. Sharing probes whether an email is registered

**Location:** `contexts/notes/src/application/sharing.service.ts:99`. The share rate limit is at `:112`, after the lookup.

**Scenario:** `People.find` matches a handle or an email. `share` answers “Nobody on LearnViaNotes has that handle or email” when nothing matches, and a different error when the person exists but cannot be shared with. A signed-in caller can test addresses. The 200-shares-per-hour limit does not apply to the miss. The per-person GraphQL cap is 600 operations a minute (`OPERATIONS_PER_MINUTE`). Password reset does not enumerate (`auth.service.ts` returns success either way). Sign-up does: an existing address is `CONFLICT` (“An account with this email already exists”).

**Fix:** Spend the share limit before the lookup, and use one message for “no such person” and “cannot share”. Not changed; it is a product copy change as well as a limit change.

### F10 — Medium. An OAuth-only account can be queued for deletion with the access token and the word DELETE

**Location:** `contexts/users/src/application/account-deletion.service.ts:41`.

**Scenario:** If `passwordHash` is set, deletion checks the password and requires `confirm` to be `DELETE`, then revokes every other session. If there is no password, the 15-minute access token plus the word DELETE schedules erasure after 14 days (`DELETION_GRACE_DAYS`). The account can cancel during the grace. A token stolen from the page (the access token is not the HttpOnly cookie) can start that clock and revoke other devices. Mail is sent to the account address.

**Fix:** For passwordless accounts, require a fresh provider sign-in (or a one-time email link) before `deletionRequestedAt` is set. Not changed; it is a product flow.

### F11 — Medium. Complexity does not multiply by list size

**Location:** `libs/graphql/src/limits.ts:96` (`simpleEstimator({ defaultComplexity: 1 })`). Depth cap is 8 (`MAX_DEPTH`).

**Scenario:** Each selected field costs 1, whatever `first` asks for. Pagination caps still apply (the security suite checks `verificationRequestsToReview(first: 100000)` returns 100). Aliases are counted, and a batch of HTTP operations is rejected (`apps/api/test/security/abuse.security.test.ts`). A query can still fan out to the maximum page of many aliased list fields until complexity 1000. That is a cost amplifier, not an auth bypass.

**Fix:** A multiplier on list fields, checked against real client queries so a legitimate note page does not start failing. Not changed; it can break clients that are under 1000 only because lists are cheap.

### F12 — Low. Institutional OTP attempts can overlap

**Location:** `contexts/users/src/application/institutional-email.service.ts:85`.

**Scenario:** The code is a 6-digit HMAC, compared with `timingSafeEqual`, expires in 15 minutes, and allows 5 misses. Resend is 3 per hour and resets the counter. The check reads `attempts` and then increments. Concurrent requests can all observe a low counter. The per-person GraphQL limit is 600 operations a minute, so one burst is hundreds of guesses, not the full million. Serial aliases do not bypass it: mutations run one after another and the counter moves.

**Fix:** Increment with a conditional update (`attempts < 5`) and treat a zero count as locked. Not changed.

### F13 — Low. Concurrent `acceptTerms` can duplicate consent rows

**Location:** `contexts/users/src/application/consent.service.ts:26`.

**Scenario:** `accept` returns early when a row exists, then `createMany`s TERMS, PRIVACY, and PUBLIC_CONTENT_LICENCE. Two requests can both pass the read. The version must still be the current one. Impact is duplicate rows, not a bypass of the terms gate. Sign-up writes the three rows in the same transaction as the user.

**Fix:** A unique `(userId, kind, version)` and an upsert. Not changed.

### F14 — Low. Partition maintenance builds a `DROP TABLE` string

**Location:** `contexts/core/src/application/learning-events.service.ts:217`.

**Scenario:** Names come from `pg_class` and must match `^LearningEvent_[0-9]{4}_[0-9]{2}$` before they are interpolated into `$executeRawUnsafe`. Application input never reaches this string. A database role that can create a matching child of `"learning"."LearningEvent"` could choose the dropped relation. That role is already a database administrator.

**Fix:** `format('%I.%I', 'learning', name)` inside a parameterized query, if you want no raw SQL here. `SET LOCAL hnsw.iterative_scan = relaxed_order` in `contexts/notes/src/application/note-chunks.ts` is a fixed string.

### F15 — Low. MX lookup treats an unexpected DNS failure as “accepts mail”

**Location:** `contexts/users/src/application/providers.ts:78`.

**Scenario:** `ENOTFOUND`, `ENODATA`, and `ESERVFAIL` refuse the domain. Any other error returns true so a DNS outage does not block registration. The verification code still has to be received. This does not make a disposable domain look academic by itself (`isPersonalOrDisposable` runs first).

**Fix:** Fail closed on timeout as well, if registration may wait. Not changed.

### F16 — Low. GitHub delivery signatures are checked; age is not

**Location:** `contexts/core/src/application/github-app.service.ts:78`. Raw body is enabled in `apps/api/src/main.ts`.

**Scenario:** HMAC-SHA256 over the exact bytes, compared with `timingSafeEqual`. A repeated `x-github-delivery` hits the primary key and returns `duplicate` without a second job. There is no timestamp skew window, so a captured delivery can be replayed until the row is kept (30 days) if the id is new to this database. The signature still has to be valid. No Stripe or Resend inbound webhook exists. Resend is outbound mail only.

**Fix:** Reject deliveries whose `X-GitHub-Delivery` timestamp header, if you start sending one, or GitHub’s documented event age, is outside a few minutes. Optional.

### F17 — Low. Operations are not restricted to persisted queries

**Location:** `libs/graphql/src/modules.ts:86`.

**Scenario:** Any document that passes depth, complexity, and validation runs. That is normal for a first-party web and mobile client. A persisted-query allowlist would shrink the anonymous surface in F5. Introspection is on only when `APP_ENV === 'development'` (`apps/api/src/app.module.ts:48`). Subgraphs are mounted under `/_subgraph` and answered 404 by `configureHttp`. `csrfPrevention: true` rejects non-JSON POSTs. HTTP batching is rejected by the security suite. Subscriptions over HTTP are refused; live updates are the WebSocket.

**Fix:** APQ or a persisted-query manifest when you want the public schema closed. Not required for the current controls.

### F18 — Low. One high advisory is ignored on purpose

**Location:** `pnpm-workspace.yaml:26` (`auditConfig.ignoreGhsas`: `GHSA-ggr8-5vv4-36mx`).

`pnpm audit --prod` reports 3 low and 13 moderate, and 1 high that this ignore removes. CI’s `pnpm audit --prod --audit-level high` exits 0 because of that ignore. The comment says `deepmerge-ts` 7 is pinned by Prisma 7.10, the bug is stack exhaustion on deeply nested input, and the CLI only merges `prisma.config.ts`, not request bodies. Drop the ignore when Prisma 8 picks up the fix.

The moderate advisories are transitive and were not upgraded in this change: `uuid` (CVE-2026-41907), `@opentelemetry/core` (CVE-2026-54285), `ip-address` (CVE-2026-111997), three `nodemailer` address-parser issues, `fast-uri` (CVE-2026-110306, CVE-2026-110180, plus two low), `qs` (CVE-2026-110816), `glob` (CVE-2026-118773), `minimatch` (CVE-2026-118764), and low `deepmerge` (CVE-2026-93753). None of these are request-reachable parsers of untrusted mail headers or of user-supplied URIs in the application code that was reviewed (`nodemailer` is a dependency of the mail stack; the app builds its own messages). Upgrading them is a dependency bump, not a contained fix.

## Controls that held

These were reviewed and are not findings.

**Authentication.** Firebase `verifyIdToken` plus `sign_in_provider === 'google.com'` and `email_verified === true` (`contexts/users/src/application/providers.ts`). Access JWTs are RS256 only, with issuer, audience, `exp`, and `iat` checked in `libs/auth-guard/src/jwt.ts` (no `none`, no HMAC confusion). Refresh tokens are 256-bit, stored as SHA-256, rotated with a conditional update, and reuse revokes the family (`contexts/users/src/application/session.service.ts`). Revoked families are denied for the access-token lifetime via Redis (`libs/redis/src/session-revocations.ts`) on both `/graphql` and `/graphql/live`. Roles in the JWT are not trusted: `setGlobalRole` reads the database (`apps/api/test/security/roles.security.test.ts`).

**Cookie.** `lvn_rt` is HttpOnly, `SameSite=Lax`, `path=/graphql`, `Secure` when the API origin is HTTPS. Apollo `csrfPrevention` plus `SameSite=Lax` blocks cross-site GraphQL POSTs. Sign-out with the cookie revokes only the family that cookie names; possessing the refresh token already owns that session.

**Authorization.** There is no global guard. Mutations that need a user use `SignedInGuard`. Object access is in the service: `NotesService.open` / `require`, `can()` in `contracts/src/domain/permissions.ts`, and the classroom, group, and file services. Federation reference resolvers for `Note`, `User`, `Group`, and `Classroom` call those same checks. `NoteVersion` is not a federation entity. `versions` and `version` return null for a reader (`contexts/notes/src/graphql/notes.resolver.ts:180`), so draft snapshots are not readable through `NoteVersion.cards` without edit access. Page images must be the editor’s `PAGE_IMAGE` on that note (`pages.service.ts` `assertImage`). Verification document URLs require `mayReview` and a file id on that request.

**Who may verify students.** `can()` allows `ACCOUNT_REVIEW_VERIFICATION` for `PLATFORM_ADMIN` without `institutionVerified`, and for a teacher only when `institutionVerified` and the student addressed them or shares their institution (`contracts/src/domain/permissions.ts:606`). `VerificationService.mayReview` refuses the subject reviewing themselves. `collegeIdQueue` gives admins the whole queue and verified teachers only their institution’s students. `gateApplies` skips the institution gate for `PLATFORM_ADMIN` (`permissions.ts:444`). Unverified teachers and students cannot review. Teacher-role applications are admin-only.

**Uploads other than F4.** Presigned PUT binds `Content-Type` and `Content-Length` (`libs/storage/src/storage.ts`). Keys are server-chosen. `completeUpload` checks the object size and magic bytes, and refuses a `COLLEGE_ID` object on the general complete path. Purpose allowlists and per-user / per-IP windows are in `files.service.ts`.

**SSRF.** User-supplied page and resource URLs go through `SafeFetcher` (public addresses only, ports 80/443, redirects re-checked, size and time caps, DNS checked on the connection’s lookup). AI provider URLs block cloud metadata and link-local at parse time and again on DNS (`contexts/ai/src/domain/provider-url.ts`, `contexts/ai/src/infrastructure/http.ts`). Private addresses stay allowed there because Ollama and LiteLLM are on the operator network, and only a platform admin can save a connection. Repository links accept only `github.com` / `gitlab.com` paths (`parseRepository`). Have I Been Pwned receives a SHA-1 prefix, not the password.

**Live WebSocket.** `/graphql/live` authenticates the access token in `connection_init`, checks revocation, caps sockets per user, and caps the payload at 64 KiB. Events are published on the viewer’s channel. The subscription payload is `kind`, `id`, and `at`.

**Terms.** Sign-up and registration require `acceptedTermsVersion` to equal `TermsVersionProvider.current()`. `acceptTerms` refuses any other version.

**Deletion and retention.** 14-day grace, password check when a password exists, sessions revoked, user row anonymised to `deleted-<id>@deleted.learnvianotes.invalid`, related rows deleted, files deleted, `UserDeleted` for the other contexts. College ID images follow the configured retention window and are removed on withdrawal.

**Webhooks and SQL.** Covered under F14 and F16. Application queries use Prisma’s tagged `$queryRaw` / `Prisma.sql`.

## Owner decisions

1. **F4.** Add a scan-only path for college ID cards (no image derivatives) and decide whether a scanner outage blocks reviewer URLs.
2. **F3 ceiling.** 300 sign-ups per network per hour is a backstop. Lower it if a campus will not register that many in an hour and the edge WAF is not doing the tight limit. 40 reset emails per network per hour is the same kind of knob.
3. **F5 and F6.** Confirm the edge rate-limits anonymous `/graphql`, or add per-network budgets for anonymous operations and for provider sign-in.
4. **F7.** Whether `scanResult = ERROR` in local mode may still be downloaded.
5. **F8.** Whether email addresses should be redacted in application logs. The unit test currently requires them to remain.
6. **F10.** Whether passwordless deletion should require a fresh provider login.
7. **F18.** Leave the Prisma `deepmerge-ts` ignore until Prisma 8, or schedule the upgrade. Moderate transitive advisories are listed above if you want them bumped separately.
8. **Squatter residue after F1.** Display name and notes created before the real owner proves the inbox are kept. Say if those should be wiped or flagged.
