# People: follows, blocks, restrictions and profiles (Phase 3, P3b-1)

- Date: 2026-10-12
- Package: `@lvn/contracts` 0.20.0 (`UserFollowed.quiet`, `UserUnfollowed.quiet`)
- Spec: §4.1, §5, §15.1; ADR-0013, ADR-0014, ADR-0016, ADR-0020, ADR-0043
- Breaking: no

## What changes for clients

| Field | What |
| --- | --- |
| `userByHandle(handle)` | A profile by handle (with or without @) or by id, for anyone. Null for restricted minors (except to themselves) |
| `User.followerMilestone` | Followers as a milestone for everyone: 1000 for 1,000+, null below |
| `User.followerCount`, `followingCount` | Exact counts, the person only |
| `User.relation` | `following`, `followedBy`, `blocked` (the viewer's own block only), `restricted`, `viewerCan { follow unfollow removeFollower block unblock restrict unrestrict }`. Null when signed out or on one's own profile |
| `User.publicNotes(kind, first, after)` | What they made public, by kind (`NOTE` for now; blogs, posts and projects in P3b-2) |
| `myFollowers`, `myFollowing` | Pages of `PersonEdge { node since }`, newest first. Restricted minors are counted, never listed |
| `myBlocked`, `myRestricted` | For settings |
| `followUser`, `unfollowUser`, `removeFollower`, `blockUser`, `unblockUser`, `restrictUser`, `unrestrictUser` | `input: { userId }` → `PersonPayload { user, userErrors }` |

How clients should use them:
- Show buttons from `relation.viewerCan`, the same rules the API applies.
- A refusal comes back as a GraphQL error with code `FORBIDDEN`:
  - "Verify your account to follow people."
  - "You can't follow this person." This message is the same for a block either way and for a restricted minor.
- A share to or from someone in a block is refused: "This note can't be shared with that person."
- New notification category in use: `FOLLOW`, with `actor` (the follower) and path `/u/<followerId>`. Profile routes
  accept an id as well as a handle. Nobody is notified by someone they restrict, or by a restricted minor.

## Behind it

- `users.Follow`, `users.Block`, `users.Restriction`. Blocking deletes follows both ways and replaces a restriction;
  it is written to the audit log.
- The `PEOPLE` facade gains `blockedIds` and `blockedBetween`. Search uses them to leave out the other person and
  their notes, both ways.
- The notes subgraph now resolves `User` for `publicNotes`. Everything else about a User stays in users.
