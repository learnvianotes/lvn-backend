Under the hood basics: core components, system execution modes, hardware abstractions, and system call lifecycles.

# Core Roles &amp; Components

> [!NOTE] Explain the role of an OS.
>
> An <strong>Operating System (OS)</strong> is system software that acts as an intermediary between user applications and physical hardware. Its primary roles include:
>
> - <strong>Resource Allocator:</strong> Fairly and efficiently allocates CPU time, memory space, I/O devices, and file storage among competing processes.
> - <strong>Control Program:</strong> Directs execution of user code, prevents errors, controls access, and prevents improper use of hardware.
> - <strong>Hardware Abstraction Layer (HAL):</strong> Hides complex, vendor-specific hardware details behind simple, standardized software APIs.

> [!NOTE] Kernel
>
> The core program of the OS that runs at all times at the lowest level. It has direct, unrestricted access to physical hardware (executes in <strong>Kernel Mode</strong>) and is responsible for process, memory, filesystem, and device management.

> [!NOTE] Shell
>
> A user-space command-line interpreter or graphical interface that translates human commands into system calls. It is not part of the kernel; it acts as a user application running in <strong>User Mode</strong>.

# System Modes &amp; Hardware Access

> [!NOTE] Difference between User Mode and Kernel Mode.
>
> Modern CPUs enforce memory and hardware protection via physical execution modes:
>
> - <strong>User Mode (Mode bit = 1):</strong> Restricted mode. The CPU cannot execute privileged instructions (such as disabling interrupts, modifying page tables, or writing directly to hardware ports). Access to memory is bounded to the process's allocated range.
> - <strong>Kernel Mode (Mode bit = 0):</strong> Unrestricted mode. The CPU can execute any machine instruction and access any physical address in the system. The core OS kernel executes here.

> [!NOTE] Why can't applications directly access hardware?
>
> If user applications had direct hardware access:
>
> - <strong>Security Violation:</strong> An application could read sensitive data directly from disk blocks belonging to other users.
> - <strong>System Instability:</strong> A bug in one application (e.g., writing to memory-mapped control registers) could corrupt physical memory or crash the entire computer.
> - <strong>Complexity:</strong> Every developer would need to write low-level code to communicate with specific disk controller chips, network cards, and screen monitors.

# System Calls &amp; Interrupts

> [!NOTE] What is a system call?
>
> A programmatic interface that allows a user-mode application to request services from the kernel (e.g., reading a file, spawning a process, sending packets). It transitions the CPU from User Mode to Kernel Mode via a controlled <strong>software interrupt/trap</strong>.

> [!NOTE] fork() vs. exec()
>
> <strong>fork():</strong> Spawns a new child process by duplicating the calling parent process's memory space, descriptors, and execution state. Both execute the next instruction.
>
> <strong>exec():</strong> Replaces the entire address space and code image of the current process with a new executable program. It does not create a new process; it overwrites the current one.

> [!NOTE] Interrupt vs. Exception
>
> <strong>Interrupt:</strong> An <em>asynchronous</em> event generated by external hardware (e.g., timer clock tick, disk write complete, key press) indicating it needs CPU attention.
>
> <strong>Exception (Trap):</strong> A <em>synchronous</em> event generated by the CPU itself during execution of an instruction due to an error (e.g., divide-by-zero, page fault) or a programmatic request (system call trap).

> [!NOTE] What is Context Switching? Why is it expensive?
>
> The mechanism of saving the CPU execution state (Program Counter, registers, stack pointer, MMU page tables) of a running process or thread, and loading the saved state of another to resume its execution.
>
> <strong>Why it is expensive:</strong>
>
> - <strong>Direct Cost:</strong> Time spent executing OS scheduler code, saving registers, and updating process state tables.
> - <strong>Indirect Cost:</strong> Flushing the <strong>Translation Lookaside Buffer (TLB)</strong> and invalidating L1/L2/L3 caches. When the new process runs, it suffers major cache misses, leading to slow instruction execution until caches are warmed up again.

# Amazon SDE-1 Follow-up Scenario

> [!NOTE]
>
> <strong>Question:</strong> Walk me through everything that happens step-by-step when your Python code runs: <br> `open("file.txt")` <br> until the file contents are returned.

> [!NOTE] Step-by-Step Kernel Execution Lifecycle
>
> 1\. Python Runtime → 2. Trap System Call → 3. Permission &amp; Inode Lookup → 4. Block Request / Context Switch → 5. Disk Controller I/O → 6. Hardware Interrupt → 7. Copy to User Space &amp; Return
>
> 1. <strong>Translation:</strong> The Python runtime translates the \`open()\` call to the low-level library function (e.g., POSIX \`open(2)\`).
> 2. <strong>Mode Transition (Trap):</strong> The library places the system call identifier for open in a CPU register and executes a software interrupt/trap instruction (e.g., \`syscall\` or \`int 0x80\`). The CPU switches the mode bit from \`1\` (User) to \`0\` (Kernel) and jumps to the kernel's system call interrupt handler.
> 3. <strong>Descriptor Allocation:</strong> The kernel's VFS (Virtual File System) checks process permissions, resolves the path \`"file.txt"\` to an <strong>Inode</strong>, allocates an entry in the system-wide open file table, and returns a unique integer File Descriptor (FD) inside the process's file table.
> 4. <strong>I/O Scheduling:</strong> The kernel initiates a read request to the device driver for the disk sectors containing \`"file.txt"\`.
> 5. <strong>Blocked State:</strong> Because disk I/O is slow (milliseconds), the kernel moves the calling process from the <strong>Running</strong> state to the <strong>Blocked/Waiting</strong> queue. The CPU executes a <strong>Context Switch</strong> to run another active process, keeping CPU utilization high.
> 6. <strong>Interrupt Trigger:</strong> The disk controller retrieves the block bytes, stores them in its buffer, and signals a physical line on the interrupt controller. The controller raises a <strong>hardware interrupt</strong>.
> 7. <strong>Interrupt Handler:</strong> The CPU halts its current instruction, jumps to the kernel's interrupt service routine (ISR). The ISR reads bytes from the controller buffer into the kernel's <strong>Page Cache</strong>.
> 8. <strong>Wake Up:</strong> The kernel updates the waiting Python process state from <strong>Blocked</strong> to <strong>Ready</strong> in the scheduler queue.
> 9. <strong>Reschedule &amp; Return:</strong> The CPU schedules the Python process. The kernel copies the file buffer data from kernel memory space to the process's user memory space, transitions back to <strong>User Mode</strong> (mode bit = 1), and return execution control back to Python.
